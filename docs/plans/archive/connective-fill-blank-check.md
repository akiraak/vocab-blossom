# 接続詞・つなぎの語句で穴埋めが作れるか検証する

## 目的・背景

接続詞・つなぎの語句 94 語を、働きごとに 10 グループにして登録した（docs/plans/archive/connective-groups.md）。
穴埋めは、もともと名詞・動詞・形容詞などを考えて作っている。つなぎの語句でも問題なく出題できるかを確かめ、ダメなら直す。

心配な点は 3 つ。

1. **文章が作れない**: サーバーは 1 語につき 3 パターンを AI に作らせ、「見出し語がちょうど 1 回」などを検証する
   （`passageProblems`。1 つでも落ちたら作り直し、2 回目も落ちたらその語は文章なし → 例文で出題、例文も駄目なら英→日）。
   - and・to・or・but・so・for・then・that is などは、文章の中のほかの場所にも出やすく「1 回」を通りにくい
   - 「…」を含む 4 語（either … or …・neither … nor …・not only … but also …・both … and …）は、見出し語の照合（`countHeadword`）で見つからない
2. **空欄が正しく作れない**: iOS は `Inflector`（Swift）で見出し語を探して空欄にする。サーバーの照合（TypeScript）と食い違うと、
   検証は通ったのに空欄にできない・違う場所を空欄にする、が起きうる（例: in addition の文章に in addition to が出る）
3. **正解が 1 つに決まらない**: マイ単語の誤答肢は同じグループの語から選ぶ。働きごとのグループなので、
   however の空欄に but・nevertheless が並ぶと、どれでも文が成り立つ。AI への指示も「誤答肢は同じ品詞のほかの語」という前提で書いてある

## 対応方針（調査）

### Phase 1: 実際に作って数える（ローカル・本番には書かない）

- スクリプト（scratchpad）で、94 語すべてについてサーバーと同じ手順（AI で作る → `passageProblems` → 落ちたら 1 回作り直す）を流す
  - AI は本番と同じ `createClaudePassageWriter`・既定のモデル。キーは g3plus-ops の `.env` から読む（画面・ログに出さない）
  - 入力は `data/groups/connectives.json`（マイ単語）と単語帳の語（同梱語）。iOS が送るのと同じ形（word・pos・meaning・example）
  - 結果（語ごとの通った／落ちた・落ちた理由・文章）を JSON に残す
- 数えること: 1 回目で通った語・作り直しで通った語・最後まで落ちた語と理由
- 通った文章で、iOS と同じ空欄の作り方ができるか（TypeScript の `findHeadword` で、見出し語の場所が 1 つに決まるか・ほかの語の一部を拾っていないか）

### Phase 2: 正解が 1 つに決まるかを見る

- Phase 1 で通った文章について、実際の出題と同じ選び方（同じグループの同じ品詞 → 同じグループ → 単語帳の語）で誤答肢の候補を並べ、
  「空欄に入れても文として成り立つ語」を AI に判定させる（判定役の指示は作る側と別にする）
- 数えること: 誤答肢の候補の中に、正解のほかにも入る語がある文章の割合。どのグループ・どの組で起きるか
- 4 択（英→日・日→英）は意味の文字列で選ぶので、意味の書き方（括弧書き）で区別できているかを目で見る

#### Phase 1 の結果（2026-11-04）

- 94 語を本番と同じ手順（Opus 5.5・3 語ずつ・落ちたら 1 回作り直す）で作った:
  **1 回目で通った 87 語・作り直しで通った 2 語・落ちた 5 語**
  - 作り直しで通った 2 語（in spite of the fact that・whereas）は、1 文になっていただけ
  - 落ちた 5 語:
    - 「…」を含む 4 語（either … or …・neither … nor …・not only … but also …・both … and …）: 2 回とも 3 パターンすべて「見出し語が 0 回」。
      照合が「…」を扱えないため（AI は正しく使っている）。今は例文も同じ理由で駄目なので、穴埋めにならず英→日で出る
    - `to`: 「見出し語が 2〜3 回」。不定詞の to のほかに、前置詞の to（go to school）も数えるため
- 通った 267 パターンで、iOS（Swift の `Inflector`）とサーバー（TypeScript）の空欄の位置を突き合わせた: **食い違い 0**
- 文章にほかのつなぎ言葉（and・to・for など）が混じるのは普通の使い方か、見出し語の一部（even if の中の if など）で、空欄の位置には影響しない

#### Phase 2 の結果（2026-11-04）

通った 265 パターン（89 語）の空欄に、同じグループのほかの語を入れても正解になるかを AI（Opus 5.5、作る側とは別の指示・文法も厳しく見る）に判定させた。

- **ほかの語も正解になる文章: 156 / 265（59%）**
- 実際の出題（マイ単語は同じグループの同じ品詞から誤答肢を 3 つ）に当てはめると、**マイ単語の穴埋めの約 44% で、正解が 2 つ以上ある選択肢になる**

| グループ | ほかの語も入る文章 | マイ単語の問題で紛れ込む確率 |
|---|---|---|
| 時 1 | 8 / 24（33%） | 33% |
| 時 2 | 7 / 22（31%） | 29% |
| 条件 | 17 / 30（56%） | 48% |
| 逆接と対比 1 | 11 / 21（52%） | 57% |
| 逆接と対比 2 | 16 / 27（59%） | 37% |
| 理由と結果 1 | 27 / 30（90%） | 63% |
| 理由と結果 2 | 13 / 27（48%） | 45% |
| 目的と選択 | 7 / 21（33%） | 21% |
| 追加と類似 | 24 / 30（80%） | 54% |
| 例示とまとめ | 26 / 33（78%） | 36% |

- 起きているのは、プランの段階で予想した言い換えのきく組（because / since、because of / due to、therefore / as a result / for this reason、
  moreover / furthermore / additionally / besides / in addition、similarly / likewise、for example / for instance、in other words / that is、
  in fact / actually、though / even though、even so / nevertheless、only if / provided that、lead to / result in、consequently / thus など）
- 例: 「This apartment is near the station. ＿＿＿＿, the rent is low, so I want to live here.」（正解 moreover）には
  also・besides・in addition・furthermore・additionally も入る
- 意味がはっきり違う組（however と but、when、unless など）は、文章の手がかりで 1 つに決まっている

### Phase 3: 直し方を決めて直す

#### 決めたこと（2026-11-05、ユーザーと）

- **「…」を含む 4 語**: 見出し語の照合で「…」を「間に何語か入ってよい」として扱う（サーバーと iOS の両方）。空欄は 2 か所以上になる
- **正解が複数になる問題**: 誤答肢の選び方を変え（下の案 A）、そのうえで**問題を作ったあとに AI で「どの選択肢が空欄に入るか」を判定し、入る語も正解にする**
  - グループの穴埋めは練習（SRS を動かさない）なので、「ほかの正解を選んで正解になると、覚えたか測れない」点は気にしない
  - 入る語を選んだときは「この文の答えは moreover。also も入ります」と見せ、言い換えられることも伝える
- **`to`**: 直さない（今も英→日で出ていて、1 語だけなので）
- **案 A（つなぎ言葉の誤答肢を、働きの違うグループから選ぶ）**: やる。言い換えのきく語がそもそも選択肢に並ばないようにし、
  それでも入ってしまう語（時の after と理由の since など）は AI の判定で正解にする
  - つなぎ言葉のグループは **名前の頭が「つなぎ言葉・」** で見分ける（グループは名前と語の ID だけを同期していて、種類の欄を足すと
    SwiftData の移行と同期の形の変更が要るため）
  - 「逆接と対比 1」と「逆接と対比 2」のように、末尾の番号だけが違うグループは同じ働きとみなして避ける（似た語を 1 と 2 に分けてあるため）
  - 出題の形式によらず誤答肢の選び方は 1 つなので、4 択（英→日・日→英・リスニング）も同じく働きの違うグループから選ぶ
- **文章の作り直し**: 判定は「文章 × 選択肢の語」ごとに別に持つので、今ためてある文章はそのまま使える。作り直しは要らない
  （「…」の 4 語は今は文章が 1 つも無いので、照合を直せば次に穴埋めを始めたときに作られる）

#### 判定をどこでするか

出題は表示の直前に組み立てていて（`SessionRunner.resolve`）、誤答肢は毎回ランダムに選ぶ。間違えた語の再出題では選択肢を作り直す。
判定は 1 回の AI の呼び出しに数秒かかるので、出題のたびに呼ぶと回答のたびに待たされる。そこで **グループの穴埋めモードだけ、出題を先に組み立てる**:

1. 文章を作る（今のまま。`PassagePreparation`）
2. 全語の問題（文章 + 4 択）を先に組み立てる
3. まだ判定していない「文章 × 選択肢」をサーバーに送り、空欄に入る選択肢を受け取る（作る画面の続きで「選択肢を確かめています」を見せる）
4. 出題する。間違えた語の再出題は、同じ問題を選択肢の並びだけ変えて出す（作り直すと判定していない選択肢が混じるため）

- 判定できなかったとき（オフライン・サーバーのエラー）は、今と同じく正解は見出し語だけで出題する
- いつもの学習（SRS のステージで穴埋めになる問題）は今のまま。判定はグループの穴埋めモードだけ

#### Step 1: 「…」を含む語の照合（サーバー・iOS）

- サーバー `server/src/words/inflect.ts`: 見出し語を「…」（と `...`）で区切り、区切りの間に 1〜6 語入ってよいパターンにする。`findHeadword`・`countHeadword` が使う
- iOS `Inflector.swift`: 同じ扱いで、見出し語の範囲を区切りごとに返す（`findHeadwordRanges` を足す。今の `findHeadword` は 1 か所目）
- iOS `QuizBuilder.blank`: 範囲ごとに空欄にする（「＿＿＿＿ tea ＿＿＿＿ coffee is fine.」のように 2 か所になる）
- `GroupEditor` の「例文に見出し語が無い」の判定も同じ照合を使う
- テスト: Vitest・Swift Testing に 4 語の例を足す。サーバーと iOS で空欄の位置が同じになることも確かめる（Phase 1 と同じ突き合わせ）

#### Step 2: つなぎ言葉の誤答肢を働きの違うグループから選ぶ（iOS、案 A）

- `QuizBuilder` に渡すグループを、ID の並びだけでなく名前も持つ形にする（今は `[[String]]`）
- 出題する語がつなぎ言葉のグループに入っていれば（マイ単語・単語帳の語どちらも）、誤答肢のプールを次の順にする:
  1. 働きの違うつなぎ言葉のグループの語（同じ品詞 → 全品詞）
  2. 今のプール（足りないとき。マイ単語は同じグループ → 単語帳、単語帳の語は同じレベル → 全体）
- 「働きが同じ」= 名前の「つなぎ言葉・」の後ろから末尾の番号（` 1`・` 2`）を除いたものが同じ。出題する語が入っているグループと、それと同じ働きのグループの語は使わない
- 今の決まり（綴り・意味が重ならない、ほかのグループのマイ単語は出さない）のうち「ほかのグループのマイ単語は出さない」は、つなぎ言葉どうしに限って外す
- テスト: Swift Testing（つなぎ言葉の語の誤答肢が働きの違うグループから選ばれる・1 と 2 の組からは選ばれない・つなぎ言葉でない語は今のまま・
  働きの違うグループが足りないときは今のプールで埋める）

#### Step 3: 判定の API（サーバー）

- `POST /api/fill-blank-checks`。1 回に 10 問まで（グループ 1 つ分を 1 回で判定できるように）。1 問は `{ id, text, answer, choices: [語] }`（`text` は見出し語の入った全文）
  - 返事は `{ results: [{ id, alsoCorrect: [語] }] }`（正解以外で空欄に入る語）
  - `model` は今の API と同じく許可リストで受ける
- 判定の指示は文章を作る側と別にする（Phase 2 の判定役と同じ考え方: 文法・意味・自然さを厳しく見て、入るか入らないかだけ答える）。
  `server/src/ai/claude-fill-blank-check.ts`
- 「文章・正解・選択肢の語」を鍵に、判定を DB にためる（新しいテーブル `fill_blank_checks`）。ためてある組は AI を呼ばない
- 回数制限は今の AI の API と同じ仕組み
- テスト: Vitest（入力の検証・ためた判定を使う・AI の失敗・偽物の判定役）。本物の AI で、Phase 2 の例（moreover の文章に also・besides が入る、
  however と but は入らない など）を数件流して、判定が Phase 2 と大きく食い違わないかを見る

#### Step 4: iOS で先に組み立てて判定し、ほかの正解も受け付ける

- `Quiz` に「ほかにも正解の語」（`alsoCorrectWordIds`）を足す。正誤は「見出し語かほかの正解を選んだか」で決める
- `SessionRunner`: 組み立て済みの問題を受け取るドリルの初期化を足す。再出題は同じ問題を選択肢の並びだけ変えて出す
- `FillBlankSessionView`・`PassagePreparation`: 文章を作り終えたら問題を組み立てて判定する（作る画面に判定の段を足す）。判定が失敗しても出題は始める
- `QuizCardView`: ほかの正解の選択肢も正解の色にし、「これも正解」と添える。ほかの正解を選んだときは「この文の答えは〜」を見せる
- 回答後の読み上げは今のまま（見出し語 → 文章）
- テスト: Swift Testing（ほかの正解を選ぶと正解になる・再出題で同じ問題が出る・判定が失敗したら見出し語だけが正解）。SwiftLint 警告 0

#### Step 1〜4 の結果（2026-11-05）

- Step 1: サーバー（`inflect.ts` の `ellipsisSegments`・`findHeadword` の `parts`）と iOS（`Inflector.findHeadwordRanges`）で「…」の区切りごとに照合し、
  `QuizBuilder.blank` は区切りごとに空欄にする（「You can have ＿＿＿＿ cake ＿＿＿＿ ice cream.」）。文章を作る指示に「…」の語の書き方を 1 行足した

  （「確かめずに始める」ボタンあり）。`Quiz.alsoCorrectWordIds`・`isCorrect(choiceIndex:)`、回答後に「これも正解」と「この文の答えは〜。〜も入ります」。
  デバッグの `fill-blank-preparing` では偽の判定役が 1 つ目の誤答肢をほかの正解にする
- Vitest 261 件・型チェック OK・Swift Testing 291 件・SwiftLint 警告 0。回答後の画面は画像に書き出して見た
- 本物の AI での確かめ（「…」の 4 語の文章が検証を通るか・判定が Phase 2 と大きく食い違わないか）は、API キーを手元で読めないので Step 5 で本番で行う
